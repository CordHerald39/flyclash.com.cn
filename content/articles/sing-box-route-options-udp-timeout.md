UDP 应用持续使用时正常，空闲一段时间后恢复却需要重连，可能与连接状态超时有关。sing-box 的路由动作提供 `udp_timeout`，但官方明确说明：设置得比入站 UDP 超时更长不会生效。因此不能只把一个数字调大就认定问题已经解决。

## 先确认断流与空闲有关

保留可用配置，记录同一应用连续通信和空闲恢复时的差别，同时查看入站、路由规则、出站及错误时间。若持续发送数据时也立即失败，应先检查 UDP 是否被目标或网络支持、规则是否命中；本步骤主要排查空闲连接状态到期，不代替网络连通性测试。

不要把 HTTP 网页加载正常当成 UDP 正常的证据。已有 TCP/UDP 分流的配置可先对照 [sing-box network 规则](/articles/sing-box-route-network-tcp-udp/)。

## 同时核对入站和路由的限制

在原入站配置及其官方字段说明中检查 UDP 超时，再检查匹配规则有没有设置 `udp_timeout`。官方路由动作页指出，路由值超过入站值时不会起到延长效果。

文档还列出协议识别后的默认超时：DNS、NTP、STUN 为 10 秒，QUIC、DTLS 为 30 秒；没有嗅探协议时，会按 53、123、443、3478 这些端口分别识别相应协议。它们是文档中的连接状态默认值，不是节点延迟或测速结果，应用持续产生新流量时的表现需要另外观察。

## 用 route-options 保留原来的出口规则

下面是一个规则对象示意，可放在已有最终路由规则之前。`route-options` 是非最终动作，设置选项后仍需要后续规则选择出口；不要删除原有出站规则。`2m` 仅是便于对照的测试值，必须与自己的入站限制和应用需求一起评估：

```json
{
  "network": "udp",
  "action": "route-options",
  "udp_timeout": "2m"
}
```

示例匹配全部 UDP。实际排查时应利用已有规则条件限制到目标应用或流量，避免无差别扩大所有连接的状态保留时间。先在配置目录执行 `sing-box check`，确认当前内核接受该动作与字段。

## 用相同条件验证并回退

1. 固定目标应用、节点、网络和空闲时长，保存原配置的复现记录。
2. 只调整匹配范围内的超时设置，重启内核后重新建立连接。
3. 复测相同空闲过程，观察新请求是否成功、日志是否出现新会话或超时；不要用一次网页刷新代替 UDP 应用测试。
4. 无改善时还原备份，继续检查系统、防火墙或上游网络是否另有更短的状态保留限制。

如果规则没有命中，应先检查顺序和匹配条件；协议日志相关概念可参考 [sing-box DNS rule action](/articles/sing-box-dns-rule-action/)。保留失败记录，避免把应用自身重连行为误写成代理节点不可用。
