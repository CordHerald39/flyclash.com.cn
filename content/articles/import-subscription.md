## 准备一份能复现的记录

本文给出 FlyClash 的操作验收流程，不臆造所有版本共用的按钮位置。开始前记录桌面 / Android、完整版本、下载仓库、系统版本、订阅格式。本文核对的桌面发行基线为 v0.2.9；不同通道界面应以实际版本为准。

准备服务方提供的 Clash / Mihomo 配置地址。第一次导入先不要额外加转换后端、筛选表达式或自定义规则，这样出现错误时只有较少变量需要排查。

## 1. 在配置入口添加并更新

以 v0.2.9 桌面源码为准，进入“配置管理”→“添加配置”，在“订阅链接”填写地址，“备注名称(可选)”填写便于识别的名称，提交添加。条目创建后可用“更新订阅”刷新；导入和“激活”是不同操作。本文核对了该版本界面文本与组件源码，没有把源码核对称为界面实测。等待本次操作完成再看结果。保存条目成功不等于地址已下载，更不等于节点可以联网。

记录更新时间、节点数量是否符合服务方说明以及日志中的第一条错误。若更新得到 HTTP 拒绝，回到地址和账户状态；若是 YAML 错误，核对配置类型；若返回 HTML，检查登录或验证页面。不要把令牌贴到公开转换站来试错。

## 2. 明确当前使用的配置和出口

在列表中对本次配置执行“激活”，等待状态更新，再检查代理策略。测试时选一个明确节点，记录其名称；若使用自动组，同时记录当前实际出口。保留此前可用配置，避免测试失败后无从恢复。

成功标准：配置可加载、目标策略组存在、实际选项符合预期。看见节点名仅证明导入了一些数据，不能代替后面两步。

## 3. 按平台确认流量入口

| 平台 / 路径 | 检查内容 | 容易误判的地方 |
| --- | --- | --- |
| 桌面系统代理 | 系统代理地址和端口与客户端一致 | 客户端窗口打开并不表示系统代理开启 |
| 应用内显式代理 | 测试应用自己的地址与端口 | 其他应用成功不能证明当前应用使用相同设置 |
| Android VPN | Android 已授权该应用建立 VPN，检查其他 VPN 状态 | 仅有运行图标不能证明目标应用已被纳入接管 |

首次验证只改变一种接管方式。桌面上未读系统代理的工具，应按其文档显式指定代理；不要直接将失败归类为 FlyClash 内核故障。

## 4. 用同一请求对齐日志

选定一个测试页面，记下时间，重新发起请求并观察连接或日志。记录目标、出口、结果；失败时保存具体错误，不只写“不行”。随后保持网络和节点不变重试一次，判断是否可稳定复现。

可使用下列记录格式，空白项必须按实际填写，不能把它当作测试结果：

~~~text
平台与版本：
配置本地名称（不含令牌）：
接管方式 / 实际端口：
请求时间 / 目标：
策略组 / 实际出口：
结果 / 脱敏错误：
恢复原配置后的结果：
~~~

## 失败后怎么回退

新订阅异常时切回之前保留的配置，恢复测试前接管方式，再验证原测试页面。不要一边恢复一边升级客户端。只有新版本复现的问题，应附版本差异和同条件对照，才有助于开发者定位。
