sing-box 出现 TLS 证书主机名不匹配时，先核对连接地址、server_name 和服务端证书分别是什么。官方 TLS 文档说明，server_name 用于验证返回证书的主机名；除 IP 地址等文档注明的情况外，它还会进入客户端握手，用于虚拟主机选择。修改连接 IP 与修改证书验证名称不是同一步操作。

## 先区分失败发生在哪一层

保留原配置，记录客户端与核心版本、失败时间和最早出现的错误。连接超时、连接被拒绝、证书名称不匹配、证书过期或证书链不受信任，各有不同的检查方向。只有日志显示进入 TLS 校验，才有理由优先检查这一层；不要把所有失败都归因于 server_name。

还要确认错误属于哪个连接：代理出口、DNS 加密连接或其他启用 TLS 的组件都可能使用相关字段。定位实际报错的组件后，再核对该组件正在使用的 tls 配置，避免修改一份同名但与故障无关的字段。

## 对照连接地址、服务名称与证书

先从你有权使用的服务配置或运营方文档取得预期的 TLS 服务名称，再核对实际配置。不能从一个无关网站随意挑选名称，也不能仅根据代理显示名称判断证书域名。

以下只展示现有组件中 tls 对象的字段形式，不是完整代理配置。service.example.com 是示例域名，必须替换为对应服务的正确名称；原组件还需要满足它自己的协议和认证要求。

```json
{
  "tls": {
    "enabled": true,
    "server_name": "service.example.com",
    "insecure": false
  }
}
```

连接地址可以因部署而采用 IP 或另一地址，但 TLS 验证名称必须与实际服务证书相符。保留原来已经确认的地址、端口与认证信息，先只核对名称。若服务器部署有多个虚拟主机，还需确认服务端根据握手名称选择的是预期证书。

## 名称正确后检查时间和信任链

当日志提示过期、尚未生效或不受信任，应检查本机时间和服务端证书状态，而非继续尝试不同域名。涉及私有证书颁发机构时，先确认服务所要求的可信证书来源，再按官方 TLS 配置与所用平台的信任方式处理。不要从陌生反馈帖复制证书来覆盖现有信任关系。

官方对 insecure 的说明是接受任意服务端证书。将其启用后连通，不能证明证书已正确，也不能作为这次修复的验收标准。应回到名称、证书有效期和信任链逐项处理，并在验证开启的条件下复测。

## 复测与恢复

检查保存后的配置并重载，重新建立连接，核对同一组件是否不再产生原证书错误，以及目标请求是否成功。若名称错误消失但连接仍失败，继续读取新的首个错误，不要把后续超时当作原名称问题的证明。

需要反馈时，提供核心版本、时间、脱敏后的错误文字以及已核对的项目，隐藏节点密码、订阅地址与私人域名。无法确认正确证书名称时恢复原配置，并向服务提供方核对部署信息。
