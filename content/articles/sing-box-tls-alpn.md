TLS 握手失败时，`alpn` 经常被误当成“开启 HTTPS”的开关。sing-box 官方共享 TLS 文档把它定义为应用层协议协商列表，入站和出站都可以出现；它需要与对端实际支持的协议相容。`alpn` 不能替代 `server_name`、证书校验或传输协议，列表写对也不等于远端一定接受。

## 先锁定实际 TLS 连接

保存原配置和最早一条握手错误，确认报错来自代理出站、DNS 加密连接还是其他 TLS 组件。连接超时、证书名称不匹配和 ALPN 协商失败属于不同层次，先定位组件再改字段。服务提供方或你管理的服务端文档是协议列表的依据，不要从无关网站复制值。

`alpn` 是数组；常见协议名称是否可用必须由端点说明确认。下面的写法只展示字段形状，`h2` 和 `http/1.1` 仅作为说明用占位，不代表任何服务的必填值：

```json
{
  "tls": {
    "enabled": true,
    "alpn": ["由服务端文档确认的协议"]
  }
}
```

## 一次只改协商列表

1. 记录现有 `server_name`、地址、端口、证书校验状态和出站标签，先备份。
2. 依据服务端文档把 `alpn` 改成明确支持的顺序，运行配置检查；不要同时改 `insecure`、指纹或传输层。
3. 完全建立一条新连接，查看日志是否进入 TLS 握手，以及协商出的协议或首个错误。
4. 若 ALPN 错误消失但证书错误出现，转查名称和信任链；若仍超时，回到地址、端口和网络路径。
5. 用原配置复测一次，确认差异只来自列表。问题未定位时恢复备份，不要把 `insecure` 当作验收条件。

观察日志时，先记下握手阶段的第一条错误和本次连接使用的出站标签，再比较修改前后的结果。若对端明确返回“不支持协议”，才继续调整列表顺序或成员；若错误停留在连接建立前，优先检查地址、端口和网络路径。多个 TLS 组件共用一份配置时，必须确认实际生效的是哪一个对象，否则容易把无关连接的日志当成证据。测试结束后关闭旧连接，清除只在内存中的临时状态，再用同一目标建立新会话。这样可以判断变化来自协商，而不是复用的旧握手。无法从服务端资料确认协议时，保持原列表并向服务维护者核实，避免盲目扩大兼容范围。

证书主机名的检查步骤见 [server_name 证书域名](/articles/sing-box-tls-server-name-certificate-check/)，指纹字段的边界见 [uTLS 指纹排查](/articles/sing-box-tls-utls-fingerprint-check/)。回滚后要关闭旧连接并重新建立会话，旧会话不能证明恢复成功。
